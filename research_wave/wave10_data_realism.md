# GridRescue 数据真实感与数字孪生可信度提升报告

**正式日期：2026-08-22**  
**用途：研究生竞赛申报、答辩与十日冲刺排期**  
**审查范围：** 场景、网络、潮流、MRV、数据目录、官方导出证据包及既有研究材料。  
**边界：** 本报告只给出可信度评估、数据工程改进清单、验收口径和试点路线；未修改生产代码或既有结果。

---

## 1. 结论先行

GridRescue 已具备“**标准配电网基准算例上的、可复跑的恢复—潮流—碳核算原型**”的可信骨架，但尚不应包装为已完成现场校准的区域配电网数字孪生。

竞赛中应采用如下定位：

> **以 MATPOWER case33bw 为公开标准网络底座，以显式工程假设和可追溯合成情景驱动的配电恢复决策数字孪生原型。**

当前优势：

1. data/case33bw.m 与 src/gridrescue/case33_data.py 将 33 节点、37 支路、P/Q、R/X、基值及 Baran–Wu/MATPOWER 来源绑定；官方导出还冻结了网络源 SHA-256。
2. artifacts/v08_official 下的 flood、heat、typhoon MRV 包含场景快照、网络快照、因子快照、运行清单、证据索引、封存文件及验证结果。
3. 官方 run_manifest 已诚实标记 data_class=E_synthetic_demo；verification.json 明确将验证界定为文件完整性和方程复算，而非第三方核证。
4. 潮流校核有可展示的物理约束证据：artifacts/powerflow_validation.csv 的 24 小时样例未报热稳或电压越限。

主要短板：

1. 灾种、故障支路、修复时长、人员距离、PV 降额、网电碳乘子和时间曲线主要来自确定性设定或均匀随机抽样。
2. 仓库中当前不存在 data/raw、evidence 或字段级 Data Card；真实测量数据为零。
3. ambient_temperature_c 仅作为场景字段序列化/导出，尚未进入负荷、热限额、设备故障率、PV 效率、储能效率或修复可达性计算。
4. sample_fault_scenarios() 从 1–32 号支路均匀抽取 2–5 个故障，PV、碳、距离、温度独立均匀抽样，未表达共因灾害、资产类型脆弱性、空间相关性及交通受阻。
5. 网络 R/X 与拓扑来自标准算例，但热限额、DER 容量和位置、关键负荷标签、功率因数均是工程假设；它们需要从代码常量升级为可审查参数台账。

十日目标不应承诺“做成现场数字孪生”，而应完成如下跃迁：

> 从“可信的合成对照实验”升级为“**数据分级明确、合成标识强制、天气—故障—修复耦合可解释、面向真实数据校准预留接口的竞赛级数字孪生**”。

## 3. 关键观察

### 3.1 当前是参数化情景，而非天气驱动场景生成

src/gridrescue/scenarios.py 直接指定故障支路、修复小时、PV 降额、碳乘子、里程和温度。hourly_profiles() 由正弦、晚峰高斯项、昼光正弦和固定随机种子组成。高温只额外加了下午负荷峰；暴雨和台风没有读取真实降雨、风速、积水或道路状态。演示稳定，但“极端天气”在现版本更像叙事标签而非可审计驱动变量。

### 3.2 温度尚未形成物理闭环

ambient_temperature_c 只出现在场景定义、序列化和测试中，不被负荷、线路热限额、故障概率、PV、储能或修复模型消费。字段虽进入 MRV 快照，却尚未改变主仿真 KPI。

### 3.3 合成蒙特卡洛没有灾害结构

当前随机场景为故障支路均匀抽取、修复时长 3–12 h、PV 降额 0.20–0.90、碳乘子 0.95–1.22、里程 15–95 km、温度 20–44°C。变量彼此独立，支路也没有架空/电缆、地势、资产健康度、开关站、可达性等属性；它适合算法压力测试，不适合宣称台风/暴雨风险分布。

### 3.4 网络的标准部分与项目映射部分需要分层治理

case33 的阻抗、负荷和常开联络线是可靠基准；DER、关键负荷、容量和 0.95 功率因数属于项目映射。network_manifest.json 已披露 capacity_assumption，是良好起点；下一步应使每个派生字段都具有参数 ID、等级、版本、理由和敏感性范围。

### 3.5 MRV 边界透明，但数据谱系尚需细化

v08 run_manifest 已记录代码包、配置、因子、网络、依赖、求解器和策略门控的 hash。它可以支撑“结果可复算”的竞赛陈述，但 sealed 不会将合成输入自动升级为实测证据。通用 evidence/data_cards、原始天气缓存、现场数据接口尚未落地。

建议每个可独立冻结资产对应一张 evidence/data_cards/<data_id>.yaml。最低字段为：

| 类别 | 必填字段 |
|---|---|
| 身份 | data_id、name、class、status、purpose |
| 覆盖 | geography、timezone、temporal_resolution、horizon、spatial_resolution |
| 来源 | publisher/source、version、retrieved_at、license、source hash |
| 生成 | upstream_data_ids、generator、generator version、seed |

| 质量 | missing rate、QA results、uncertainty、known limitations |
| 声明边界 | allowed claims、prohibited claims、derived class |

视觉规则：

- **B 类公开标准/历史再分析**：显示来源、版本、下载 hash。
- **D 类工程假设**：显示取值、区间和理由。
- **E 类合成/仿真**：显示生成器、seed、上游 Data Card。
- **DERIVED**：显示“继承最弱上游等级”，例如 DERIVED[E]。
- 所有图表和导出行均保留 data_class、data_id、version；无标签即不得进入正式展示。


## 6. 天气—故障—修复—调度的最小可信闭环

十日内无需宣称真实停电预测，但必须形成下列可解释链：

~~~text
冻结天气小时序列
→ 按天气区映射到资产
→ 资产脆弱性先验与区域共同冲击
→ 小时故障概率/故障样本
→ 天气与道路条件影响修复时长
→ 同时驱动 PV、负荷、热限额
→ 恢复优化与潮流校核
→ KPI、MRV、数据等级继承
~~~

### 6.1 推荐特征

- 降雨：R1、6 h 滚动 R6、24 h 滚动 R24。
- 风：平均风速 W、阵风 G。
- 温度：T、高温超阈 H=max(0,T−T_hot)。
- 可选陆面代理：土壤湿度或积水持续时间。
- 可达性：按道路区或统一 access_multiplier。

### 6.2 最小 hazard 模型

对资产 i、小时 t：

~~~text
lambda(i,t) = lambda0(i) * asset_multiplier(i)
              * exp(beta_r*ln(1+R24) + beta_w*[W-W0]+
                    + beta_g*[G-G0]+ + beta_T*H)

p(i,t) = 1 - exp(-lambda(i,t) * delta_t)
~~~

所有 lambda0、beta、asset multiplier、阈值在十日版明确标为 D 类先验，禁止写成现场标定参数。

区域共同冲击可采用：

~~~text
p'(i,t) = sigmoid(logit(p(i,t)) + rho(zone(i))*Z(t))
~~~

它能避免台风/暴雨出现彼此独立、随机撒点式的故障图。

### 6.3 四条同步耦合规则

1. 修复：repair = base_asset_repair × weather_multiplier × access_multiplier，并输出分解。
2. PV：优先 GHI；没有 GHI 时使用明确标识的参数化 fallback。
3. 负荷：典型日基线乘温敏项，温敏项可单独开关。
4. 热限额：MVP 使用“高温/低风只减额、不增额”的简化 derating；完整动态热额定列为后续。

## 8. 统一验收门槛

### A. 数据与谱系门

1. 展示的全部输入字段具有 data_id、单位、等级、版本、来源/假设、时间空间覆盖。
2. 派生结果自动携带最弱上游等级。
3. 未标注等级、缺 hash 或缺版本的天气/因子/情景不得进入正式导出。
4. 合成情景、天气回放、现场校准三类结果不得在同一均值中混报。

### B. 天气与场景门

1. 天气序列连续、无缺失、时区唯一、单位通过 QA。
2. 天气输入必须可沿 hazard→fault/repair→PV/load/thermal→KPI 追溯到数值变化。
3. 增强降雨、风速或高温时，相关 hazard 不下降；固定 seed 下场景可完整复现。
4. 相关故障样本保存 rho、zone shock、资产先验和随机状态。

### C. 网络与物理门

1. case33 原始字段与项目假设字段清晰区分。
2. 每个非原始网络参数都有范围与敏感性结果。
3. 所有展示策略都通过径向性、连通性、热限额和电压检查。
4. 至少三组基准工况与外部潮流实现对照，误差和版本可复算。

### D. MRV 与答辩门

1. 每个 run 记录天气、网络、因子、场景、参数、seed、代码、环境及输出 hash。
2. sealed 旁固定说明“文件完整性/公式复算，不等于现场测量或第三方核证”。
3. 减排只在同服务边界/门控通过时显示；其他情况下仅显示碳清单与服务差异。
4. 60 秒演示链：来源卡 → 天气曲线 → hazard/故障 → 恢复动作 → 物理校核 → MRV。

## 9. 真实数据试点路线

### 9.1 试点定位

选择一个单馈线或园区级、非敏感的脱敏试点，先做“离线回放 + 预案比较 + 校准评估”，不直接控制实际开关。

### 9.2 最小数据包

| 数据包 | 最低字段 | 用途 |
|---|---|---|
| 资产台账 | 匿名 asset ID、类型、额定、投运年、开关/馈线关系、区域 | 脆弱性、热限额、空间映射 |
| SCADA/AMI 聚合 | 15 min/1 h P/Q、开关状态、DER、质量标记 | 负荷/PV/潮流校准 |
| 故障/抢修工单 | 故障时间、设备类型、到场/隔离/修复/送电、原因代码 | 故障与修复校准 |
| 气象 | 站点/ERA5/CLDAS 的温度、雨、风、辐照 | 联合风险与交叉核验 |
| 能源/碳 | 柴油油单/发电量、车辆里程、购电因子版本 | 真实 MRV 对账 |

### 9.3 三阶段

1. **数据治理（2–4 周）**：确定脱敏、最小化采集、访问控制、保留期、字段字典、缺失和异常处理。
2. **离线校准（1–3 个月）**：先验证负荷、故障发生、修复时长和潮流，再讨论策略收益。
3. **影子运行（1–2 个灾害季）**：系统仅生成建议与证据包，值班人员独立决策；记录建议、实际动作与偏差。

### 9.4 校准成功定义

- 负荷：留出日 MAPE/峰值误差与朴素典型日基线对比。
- 故障：Brier/AUC 或 Poisson deviance 优于常数基线；数据量不足时保留先验与区间。
- 修复：P50/P90 偏差和分设备类型残差可解释。
- 潮流：电压/损耗误差有对照与质量标记。
- 策略：报告“历史条件下的离线反事实差异”，不写成实际已经实现的减排。

## 10. 竞赛最终表述建议

**建议使用：**

> “GridRescue 以公开 IEEE 33 节点基准网络构建可复跑的恢复数字孪生。项目将公开历史天气回放、显式工程先验、故障—修复相关性、潮流约束和方案级 MRV 统一到同一证据链中；所有合成参数、工程假设与派生结果均按数据等级标识。当前验证证明其用于基准算例上的策略比较、敏感性分析与预案推演，真实馈线校准通过工单、SCADA、资产台账与气象数据的试点路线逐步完成。”

**避免使用：**

- “已用真实武汉配电网数据验证”
- “已预测真实台风停电率”
- “实时区域碳因子”
- “现场实测减排”
- “MRV 已完成第三方核证”
- “IEEE 标准支路额定/DER 配置”

## 11. 最终优先级

**十日必须交付：** Data Card、合成标识、历史天气冻结、天气 QA、weather→hazard、资产属性、相关故障、天气修复、温度闭环、MRV 谱系链接。  

**十日内完成即显著加分：** GHI/PV、负荷温敏、简化动态热额定、不确定性区间、外部潮流对照、数据就绪度看板。  

**赛后真实化主线：** 工单、SCADA/AMI、资产台账、GPS 修复记录和气象交叉验证驱动的离线校准与影子运行。

此排序最大限度提高数字孪生可信度，同时避免把当前标准算例和合成情景错误包装为现场实证。
